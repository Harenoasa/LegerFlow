# LedgerFlow 项目设计书

## 1. 架构决策

采用**模块化单体**。一个 Spring Boot 后端进程负责交易 API、Mock 支付和后台任务，一个 MySQL 库承载交易事务。Vue 独立运行。先完成正确性和 MySQL 压测基线，再接 Kafka 做异步记账，最后将 Elasticsearch 作为可选的商品搜索实验。

| 方案 | 在本项目中的取舍 |
| --- | --- |
| 按 Controller、Service、Mapper 全局分包的单体 | 启动简单，适合临时原型。当前订单、库存和支付已经有不同的状态机，继续按技术层堆代码会增加跨域写表的维护成本。 |
| 模块化单体 | 保留本地事务，按业务职责组织代码。可先用 Java 包划分边界，用同一个部署物压测单实例与多实例。推荐作为主线。 |
| 多个独立微服务 | 适合独立部署、扩缩容或隔离有明确价值的场景。若拆散下单、预留和支付结算，会引入跨库一致性与补偿，热点 SKU 行锁也不会因此消失。适合后续单独做对照实验。 |

首先按包划分业务，Maven 构建模块与部署边界可以独立演进。合并现有两个启动入口时，迁移到一个可执行应用并沿用现有表和接口路径，取消旧后端运行入口。先保留 Maven 目录以降低搬迁成本也可以，但应有明确的过渡终点。后续有独立扩容证据时，优先把 Kafka 记账消费者作为单独进程验证；如果要验证真正的数据所有权隔离，再让它独占账本库。订单、库存和支付继续共享交易库及本地事务。若只是消费者 CPU 或连接池争抢，先对比同进程资源隔离与独立进程两种效果。

## 3. 模块与数据归属

| 模块 | 拥有的数据和操作 |
| --- | --- |
| `catalog` | 商品 SPU/SKU、分类等；提供商品查询和下单所需的商品快照数据。 |
| `inventory` | `inventory`、`inventory_log`；提供预留、核销与释放三种操作。 |
| `order` | `orders`、`order_item`、`order_status_log`；负责下单、归属校验、订单状态、超时扫描。 |
| `payment` | 支付尝试、渠道流水、回调日志、退款单；负责 Mock 渠道、到账确认和退款执行。 |
| `checkout` | 编排跨模块交易，定义本地事务边界，调用各模块公开方法。自身没有表，也没有第二套对外业务 API。 |
| `outbox` | `outbox_event` 及统一追加、投递机制。由发生业务变更的事务调用追加。 |
| `ledger`（Kafka 阶段） | 记账凭证、分录；复用 `processed_event` 做消费去重。 |
| `catalog.search`（ES 实验） | 商品搜索的可重建索引和索引同步逻辑；复用商品搜索 API。 |

Mapper 和实体留在所属模块，跨模块用方法与值对象交互。已有地址校验可以保留在下单侧的地址读取接口中，等需要地址管理时再划出对应模块。通知、营销、售后、发货延后，已有表结构可保留供数据库练习。Flyway 只由后端部署物管理，保留 V1–V8 历史，新增变更用后续迁移。Mock 和 `X-User-Id` 仅用于本地演示与压测。

## 4. 交易流程与一致性

### 4.1 下单与幂等

- 沿用 `POST /api/orders` 和 `Idempotency-Key`。按 `(userId, token)` 查询；校验 token 长度及字符范围与 V7 字段一致。
- 请求指纹包含地址 ID、按 SKU 合并并排序的商品数量、规范化金额与备注。明确空值和金额小数位的规范化约定，SHA-256 计算输入使用稳定序列化。相同用户和键、相同指纹返回原订单；内容不同返回 409。兼容 V7 以前没有 token 的订单；已有 token 但无指纹的历史行无法可靠判定请求等价，命中后提示查原订单，安全拒绝本次重放。
- 同一事务写订单、明细、状态日志、库存余额与库存流水。按 SKU ID 升序锁库存并条件变更 `available → locked`，任一行失败回滚整单。控制单次明细数、合并后数量与金额上限。唯一键负责并发仲裁。仅捕获指定幂等唯一键冲突，退出原事务后在新事务回读胜出的记录并比对指纹。
- 增加 `GET /api/orders/{orderNo}`，按用户归属读取 MySQL。首次创建返回 201；重放建议返回 200 及当前状态，前端统一接受成功响应。前端在同一次提交的网络超时重试中保留同一键，业务冲突由页面确认后再发起新的购买意图。

### 4.2 支付、关单与退款

采用明确的学习项目规则：**回调在持订单锁时读取服务端 UTC 时间，只有该时刻严格早于 `expire_at` 且订单仍待支付，才能结算。** 即使渠道报告在截止前付款，回调处理时已过期也走退款。这个规则便于复现竞态，真实渠道接入时要依据渠道查询与支付协议另行定义。

| 触发 | 订单及库存 | 支付与退款 |
| --- | --- | --- |
| 用户发起支付 | 校验订单归属、有效期、应付金额。 | 创建或复用支付尝试。一期只支持 Mock 单渠道。支付 POST 要求 token，重试按订单和 token 查原支付尝试；不同 token 的同渠道请求如被合并到同一活跃尝试，需要持久化 token 映射，或明确返回可查询的活跃尝试冲突。首版采用后者以复用 V8 约束。预下单和重试使用同一 `paymentNo` 作为渠道幂等键，渠道调用在本地事务外。 |
| 明确失败回调 | 订单继续待支付，库存继续预留，可用新 token 再支付。 | 幂等标记该尝试失败。渠道状态未知时保留可查可重试状态。 |
| 到期前首次有效到账 | 订单变 `PAID`，设置唯一结算支付号；`locked → sold`，写日志。 | 记录支付成功及渠道流水，关闭其他待支付尝试，写成功 Outbox。 |
| 超时关单 | 扫描 `(order_status, expire_at)`，短事务逐单加锁复查，`PENDING_PAYMENT → CANCELLED`，`locked → available`，写日志。 | 关闭待支付尝试；若同一订单已完成结算，任务无操作。 |
| 过期或已结算后另一笔真实到账 | 若订单仍待支付但已过期，直接复用同一个关单操作；其余情况保留订单及库存状态。 | 记录真实到账，创建一笔针对该支付的全额退款单。退款成功后仍保留原订单状态。 |

跨模块事务按订单行 → 支付行 → 按 SKU ID 排序的库存行执行。其中同一个订单先取得订单锁；支付单最好按 ID 稳定访问。重复通知按渠道及通知 ID 去重，支付记录还需用渠道及外部交易号保护到账身份，防止同一流水关联两笔支付；身份、金额冲突留存异常并核查。支付单此前失败或关闭也可能收到真实成功，现有 Mapper 已允许这类状态记录到账；回调决策应以锁内订单状态和期限为准。回调成功响应以事务提交为准。

确认到账后，重复通知不会重建退款。追加一条退款业务唯一约束表达「同一支付的自动全额退款只有一单」，并在原退款单上重试。退款 worker 扫描退款表，用短事务领取租约，事务外用 `refundNo` 作为渠道幂等键调用 Mock，短事务确认结果。Mock 需要能按同一退款号返回已确认结果；发生超时先用退款号查证或幂等重试。只有确认实际退回才标记成功并同事务追加事件。退款表负责任务状态，Kafka 传递已发生的事实。读写支付详情沿用现有接口并校验归属，前端通过查单展示交易结果。

## 5. Kafka 学习场景：交易事实驱动记账

Kafka 用在已提交的交易事实向记账模块传递这一处。用户主动发起支付，MySQL 回调事务完成订单与库存结算；开启或关闭 Kafka 投递都遵守相同的交易规则。Kafka 关闭时，已追加的 Outbox 继续积压。阶段一的基线与阶段二带投递、记账的压测应分别记录。

1. **认识 Topic、Key 和消费组。** 沿用支付与退款 Topic。首版记账使用一个消费组订阅两者。支付 Topic 复用 `PAYMENT_SUCCEEDED`（已结算到账）和 `PAYMENT_LATE_OR_DUPLICATE`（待退到账）；退款 Topic 在退款确认时追加 `REFUND_SUCCEEDED`。支付失败事件可保留，记账跳过。已有 JSON 信封复用 `eventId`、`eventType`、`eventVersion`、`occurredAt` 和业务载荷，明确 UTC 时间格式及金额精度。到账事件至少包含订单号、支付号、金额和渠道流水号，退款成功事件至少包含订单号、退款号、原支付号与退款金额。业务键使用 `orderNo`。同一 Topic 分区内按写入顺序读取，跨 Topic、Outbox 重试及多发布器场景按可能乱序设计。[Apache Kafka 官方文档](https://kafka.apache.org/documentation/)
2. **练习 Outbox 恢复。** 业务与 Outbox 行同事务提交。发布器用短事务领取一小批待投递或租约到期的行，释放数据库锁后发送，收到 Kafka 确认后以领取标识条件更新。超时重试并保留原 `eventId`，退避带上限，长期失败告警并支持人工恢复。发布完成前宕机可能导致重复投递。Outbox 监控待发量、最老待发时长和失败次数。单 Broker 可用于本地练习，集群容错能力需另测。
3. **练习消费幂等。** 消费者在一个 MySQL 事务内写 `processed_event` 和账本，提交后才确认消费进度。幂等键为 `(consumer_group, event_id)`，账本还要有唯一 `(凭证类型, 来源业务号)`；唯一键命中时核对金额与业务含义，一致才视为已处理。提交后、确认 offset 前宕机的重放应得到相同账本结果。瞬时故障重试，无法解析或持续失败的事件发到 DLT，确认 DLT 已接收后再推进原消息进度。修复后保留原事件 ID 重放，避免重复过账。
4. **练习复式记账与对账。** 使用简化演示科目：订单结算到账借记渠道资金、贷记订单结算；待退到账借记渠道资金、贷记应退款；退款成功借记应退款、贷记渠道资金。每笔凭证借贷平衡，到账按 `paymentNo`、退款按 `refundNo` 去重。每笔事实独立过账，兼容退款事件先到；短时科目余额可能偏离，等两侧积压清零后按 `paymentNo` 对账。比较支付成功本金、订单结算归属、退款成功金额与账本对应凭证，报告缺失、重复或金额不符。账户科目只服务本地模拟。

记账启用时，优先用迁移后新建的演示交易验证全链路。若要包含历史批次，先定义起账范围并核对已有 Outbox 和支付/退款事实，再用同一个入口补发缺失事件，业务唯一键保持一致。

## 6. Elasticsearch 学习场景：商品搜索

一期增加统一商品搜索能力，例如 `GET /api/products?q=&categoryId=&limit=`。无关键词时由 MySQL 提供列表，有关键词时走部署时选定的搜索实现。两种实现统一使用有上限的浅分页，例如 page 从 1 起算，limit 最大 50，仅允许浏览前 1,000 条结果，并以 SPU ID 作为排序同分时的稳定次序。先用已有 MySQL ngram 实现标题关键词查询并将前端输入接入该接口，再实现一个可切换的 ES 实验后端，替换同一接口下的关键词搜索实现。订单号查单、用户订单分页、金额状态查询和账本对账继续使用 MySQL。真实价格和库存以交易时的 MySQL 校验为准。

- **入门阶段**：使用较大的可复现商品集和固定关键词样例，先暂停商品编辑和导入，用 MySQL 全量导出到新索引，按 SPU ID 作为文档 ID。标题和品牌用于关键词、相关度，分类及上下架用于过滤；列表实时价格和可售量由 MySQL 批量补齐，按命中顺序返回。使用 `_analyze` 检查中文词元，记录关键词命中质量和 P95；对比同等数据与查询条件下的 MySQL，标题搜索进行直接对照，品牌检索作为 ES 的附加能力单独验收。Bulk 要检查每条响应，失败项重试，验证样本和数量后切换索引别名。[Elastic 搜索 API 文档](https://www.elastic.co/docs/solutions/search/apis-and-tools)、[Bulk API](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-bulk)
- **增量扩展**：只有做了商品写入功能后才接增量。商品事务更新 SPU 级单调版本，并通过同一 Outbox 写入带版本的搜索字段快照；商品事件进入独立 Topic，索引消费者按 SPU ID 外部版本写入。重复和旧版本事件不会覆盖较新记录。下架以带版本的不可见文档表达，过滤该状态，避免迟到事件把商品恢复成可见。ES 刷新有延迟，监控从商品提交到搜索可见的时间。ES 停机时，交易继续，搜索实验返回明确的暂不可用状态；恢复后追赶积压。全量重建沿用暂停商品写入、排空此前增量、从 MySQL 重建并切换别名的步骤，切换成功后再恢复写入。[Elastic 近实时搜索](https://www.elastic.co/docs/manage-data/data-store/near-real-time-search)、[外部版本写入 API](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-index)

## 7. 实施顺序与验收

| 阶段 | 交付 | 通过条件 |
| --- | --- | --- |
| A. 交易闭环 | 一个后端部署物、下单幂等、查单、模拟收银台、到期关单、晚到退款执行 | 同键并发只生成一单，两用户同键互不干扰，异请求同键报冲突；多 SKU 部分失败全回滚；支付成功与超时竞态只允许核销或释放其中一种；重复通知及退款重试资金只处理一次。 |
| B. MySQL 压测 | 可重复的数据准备与负载脚本，记录订单、支付和混合负载基线 | 能定位限制吞吐的资源，并给出一项改动前后对照，负载结束后交易与库存对账通过。 |
| C. Kafka 和记账 | 在现有 Compose 基础上提供可选 Kafka 环境，复用 Outbox 和消费去重表，完成凭证与对账 | Broker 暂停后恢复并清空积压；在发送确认后和消费者数据库提交后分别模拟崩溃，重放得到单份凭证；验证退款乱序、毒消息隔离与恢复。 |
| D. 可选 ES 实验 | 同一商品搜索接口可切换 MySQL 和 ES，从 MySQL 批量建索引 | 验证中文关键词、分类过滤、排序与分页，比较两后端结果和耗时；若做增量，验证重复/乱序、下架、故障积压和重建。 |
| E. 可选拆分实验 | 以同一负载对比记账消费者同进程与独立进程 | 记录 CPU、连接池、端到端记账延迟和交易 P99，结合部署与排障成本决定是否保留拆分。 |

### 压测方案

- 选一种工具，例如 k6。每轮用独立测试库，固定 seed、数据规模、连接池、机器配置、预热和统计窗口。可复用 [库存准备脚本](../db/demo/loadtest-stock.sql) 做吞吐负载；它直接改可售库存且不写流水，同一轮要记录初值，验证库存流水时用带准确基线的数据集，并执行适用于该数据集的对账查询。
- 分别测均匀 SKU 和单热点 SKU；有足量库存的吞吐场景，与有限库存、并发重复请求、支付和关单竞态的正确性场景分开。正常流量每次购买使用新 token，网络重试复用原 token。混合负载从下单响应取得订单号再建支付单、调用 Mock。用相同到达率分档比较，并记录压测机饱和或未能发送的请求。
- 报告实际请求速率、成功订单/结算每秒数、P95/P99、缺货/预期冲突/系统错误各自占比，以及 MySQL 行锁等待、死锁、慢 SQL、连接池等待、CPU。Kafka 阶段加 Outbox 最老待发时长、消费滞后及到账到入账耗时，ES 阶段单独测搜索与索引延迟。测单实例与多实例时保证订单/支付号生成配置不会跨实例冲突，且 MySQL 总连接数可比。
- 结合 [现有对账 SQL](../db/queries/02_consistency.sql) 检查余额非负、待支付占用、已支付核销、关单释放、订单结算唯一与资金退款上限，并补充按订单和 SKU 的库存操作对账。引入 Kafka 后待积压清零再核对凭证与源事实。一次只调整一个主要变量，例如热点锁内 SQL 数量，报告实际差异、代价与适用负载。

最终项目经验以交易正确性测试、故障恢复演示和实测报告为依据。核心交付做到阶段 C 即可完整展示高并发下的交易一致性、可靠投递、幂等消费和对账。ES 提供一条独立的搜索学习线，可按时间投入推进。
